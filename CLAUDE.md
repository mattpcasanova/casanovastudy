# Casanova Study

## Project Overview
Next.js 15 application (using Turbopack) for creating AI-powered study guides. Users can upload documents and generate personalized study materials.

## Tech Stack
- **Framework**: Next.js 15 with App Router
- **Language**: TypeScript
- **Database**: Supabase (PostgreSQL)
- **Auth**: Supabase Auth with email confirmation + Google sign-in (Clever SSO code exists, keys removed)
- **Styling**: Tailwind CSS + shadcn/ui components
- **AI**: Claude API for study guide generation
- **File Storage**: Supabase Storage (private `uploads` bucket; the scanner inbox uses `scan-inbox`)

## Key Directories
- `app/` - Next.js app router pages and API routes
- `app/auth/` - Authentication pages (signin, signup, clever callback)
- `app/api/auth/` - Auth API routes (Clever OAuth)
- `components/` - React components (shadcn/ui in `components/ui/`)
- `lib/` - Core utilities (auth.tsx, supabase.ts, supabase-server.ts)
- `supabase/migrations/` - Database migrations (run in Supabase Dashboard)

## Database Schema
- `user_profiles` - User data (id, email, user_type, first_name, last_name, birth_date, clever_id, pref_* grading defaults)
- `study_guides` - Generated study guides (linked to user_id)
- `grading_results` - Graded exams (also the gradebook projection target for mastery quizzes)
- `classes`, `class_enrollments` - Classes with 6-char enrollment codes
- `study_guides.format` includes 'adaptive' (adaptive practice; see Known Issues)
- `assignments` (+ `assignment_class_links`, `assignment_submissions`) - `type` column: 'file_upload' (default) | 'mastery_quiz'
- `concepts`, `question_bank_questions`, `question_review_events` - Teacher question bank; questions have source (manual/ai_suggested/ai_extracted/ai_runtime) and status (suggested/approved/declined/archived); review events store approve/edit/decline signals
- `assignment_mastery_config`, `assignment_mastery_concepts` - Per-assignment mastery settings + concept links
- `mastery_attempts`, `mastery_attempt_concepts`, `mastery_responses` - One resumable attempt per (assignment, student); responses freeze a question_snapshot at serve time (answer NULL = resumable); students have NO SELECT on responses/bank (answers live there — API strips them)

## Mastery Quizzes (adaptive assignments)
Teacher posts a 'Mastery Quiz' assignment; students loop through concept-tagged
questions until each concept hits the threshold (default 80% over the last 5
answers, min 3 answered; cap 15/concept then partial credit).
- Engine: `lib/mastery/engine.ts` (pure functions, unit-tested in engine.test.ts)
- Round construction/AI: `lib/mastery/rounds.ts`, `lib/mastery/ai.ts` (question
  generation + extraction on claude-sonnet-5; SA grading on claude-haiku-4-5
  via `ClaudeService.gradeShortAnswer`)
- Gradebook projection: `lib/mastery/finalize.ts` writes grading_results +
  flips assignment_submissions — existing gradebook needs no changes
- Trust gradient: all AI questions land as status='suggested' until the teacher
  approves (runtime-generated ones too); review events are captured for future tuning
- Question bank UI: `/teacher/question-bank` (server components + client islands
  in `components/question-bank/`); player in `components/mastery/`
- Guardrails: 150 AI-graded short answers/student/day; runtime generation capped
  at 10/concept/attempt; extract route only accepts Cloudinary URLs

## Authentication Flow

### Email/Password Auth
1. User signs up → Creates auth.users entry + user_profiles row
2. Email confirmation required (Supabase sends email)
3. User confirms → Can sign in
4. Session stored in **cookies** (browser client is `@supabase/ssr` `createBrowserClient`), not localStorage

### Google sign-in (2026-10-13)
1. "Continue with Google" (sign-in) / "Sign up with Google" (sign-up, after the student/teacher step) → `signInWithGoogle({ next, role })` in `lib/auth.tsx` → Supabase OAuth (`prompt: select_account`)
2. Google returns to `/auth/callback?next=&role=` (client page): session from the PKCE code, then existing profile → `next`; no profile → insert one from Google's `given_name`/`family_name` with the role from sign-up, or ask with `RolePicker` (sign-in page path), then `/?welcome=1`
3. Students have no birth date yet, so `AuthGate` sends them to `/consent` (same COPPA rules; Google is NOT school consent)
4. Same email as an existing password account: Supabase links the identities, so the old profile is used
- Setup: Google Cloud OAuth client (redirect URI `https://<project>.supabase.co/auth/v1/callback`), Google enabled in Supabase Auth → Providers, and `/auth/callback` covered by Supabase's Redirect URLs (prod + `http://localhost:3000/**`)

### Clever SSO (Colegia)
**Hidden 2026-10-13**: the Colegia button was removed from sign-in and sign-up (`ColegiaButton` in `components/auth/auth-ui.tsx` and the callback route still exist; re-add the button to bring it back).
1. User clicks "Log in with Colegia" → Redirects to Clever OAuth
2. If district_id configured → Uses instant-login (bypasses school search)
3. User authenticates with Clever → Redirects to `/auth/clever/callback`
4. Callback calls `/api/auth/clever` → Exchanges code for token
5. API creates/updates Supabase user using admin API
6. Returns magic link → User signed in

**Note**: District must approve the app in Clever dashboard before users can authenticate.

## Auth Implementation Details
- `lib/auth.tsx` - AuthProvider with useContext
- Uses `isSigningOutRef` (useRef) to prevent profile fetches during logout
- `onAuthStateChange` filters events: only fetches profile for SIGNED_IN, USER_UPDATED, and TOKEN_REFRESHED (when no user)
- Sign out clears user state immediately before calling Supabase

- **Batch grading (2026-10-03)**: `/grade-exam/batch` grades a whole class set (link on `/grade-exam`). Flow: teacher drops the mark scheme + the stack (photos in any format, scanned PDFs, Word files) → pages prepared in the browser (`prepareMaterials`, `pdfMode: 'images'`), sorted in natural file-name order (camera-roll order), uploaded to Cloudinary → `POST /api/grade-batch/split` reads the top of each page with Haiku (`ClaudeService.readPageHeader`, ~$0.002/page) → `lib/grading/batch.ts` (pure, unit-tested) `splitPoints`/`groupPages`: students write their name on page 1 only, so a named (or first-looking) page starts a new paper; the same name repeated doesn't split. The review screen derives groups from split flags (scissors toggle per page, remove page, rename). Grading runs in the browser, first paper alone (writes the prompt cache) then 3 at a time, via `POST /api/grade-batch/paper` (fetches pages, `gradePaper`, saves `grading_results` with `batch_id`, migration 043). `/grade-exam/batch/[id]` (+ `GET /api/grade-batch/[id]`, owner only) is the class results table with CSV (`resultsCsv`). The shared engine `lib/grading/grade-paper.ts` (`gradePaper`: grade, completeness check via the mark-scheme summary, follow-up for missed questions, phantom-question filter, totals) is also used by `/api/grade-exam-stream`. The grader caches instructions + mark scheme (`cache_control` on the last mark-scheme block). Measured: 7-mark 1-2 page quiz ≈ 6-10 s and ~$0.015-0.03 per paper. Keep the tab open while it grades. **2026-10-05**: both grading pages open with `GradingModeSwitch` (Whole class first, One student); the nav Grading menu has "Grade a Class" (default) + "Grade One Paper". `readPageHeader` also returns `title`/`course`/`period`; batch fills empty Exam details (now shown on the review screen) with `mostCommon` over the pages, the single grader fills student name/title/class/period from the first page via `POST /api/grading/read-header` (one base64 JPEG). `splitNameAndPeriod` turns "Sean Miller P2" into name + period. With **no mark scheme**, batch drafts one answer key from the first paper (`POST /api/grade-batch/answer-key`, `ClaudeService.draftAnswerKey`, Sonnet 5, ~20-60 s, ~$0.05-0.15) shown editable on the review screen; every paper is graded against it (sent as the mark-scheme text, so totals match and the prefix caches). Without it, each paper invented its own scheme (real 5-student run: totals 32-49, 15 vs 26 questions, 3 of 5 needed the follow-up pass). Real timing for 9-page handwritten papers was ~2-2.5 min each on Sonnet 5 (~55 s on Sonnet 5.5); `estimateGradingSeconds` (~15 s + 5 s/page, first alone then 5 at a time) drives the time shown before and during grading. `MarkSchemeNudge` is the amber "highly recommended" box. **Live progress + class report (2026-10-05)**: `/api/grade-batch/paper` streams NDJSON (`status` / `progress {graded,total}` from `markingProgress` / `done` / `error`; plan blocks still come back as plain 403 JSON before the stream); the page reads it with `readNdjson`, shows per-paper status ("Reading 9 pages", "Marking question 7 of 15", elapsed), overall elapsed + time left (`remainingSeconds`, re-timed from finished papers via `measuredSecondsPerPage`), and retries a failed paper once after 5 s. `CONCURRENCY = 5` (first paper still alone to write the cache). Class report on `/grade-exam/batch/[id]` (`components/grading/class-report.tsx`): numbers from `lib/grading/insights.ts` (pure, unit-tested: `questionStats`, `topicStats`, `markedConsistently`, `insightsSignature`, `insightsInput` numbers students, never names them) + AI words from `POST /api/grade-batch/[id]/insights` (`ClaudeService.classInsights`, Sonnet 5 thinking off, ~15 s, ~$0.05: summary, topics grouping question labels, struggles, reteach). Saved in `grading_batch_insights` (migration 046, owner SELECT, service-role writes) with a signature of the marks; written automatically on first visit, and offered again ("Update for the new marks") when a mark changes. Inconsistently marked batches (no shared scheme) get a warning and the per-question table folds away (one real batch had 86 labels for ~20 questions).
- **Splitting a phone-photo stack into papers (2026-10-26)**: a real 228-page stack (25 nine-page AP Chem papers, iPhone photos in camera-roll order) came back as 45 "students" with 15 roster names unmatched. Two causes: (1) inside pages photographed held up in front of the stack show the next paper's cover underneath, and the Haiku page read returned that name (and, given the roster, picked roster names for pages with no name at all; an example name in the prompt, "Sean Miller", came back on nameless pages); (2) every named page was treated as a first page. Now: `readPageHeader` (Haiku, every page) is told to read only the sheet that fills the photo and that a nameless page stays null; a name no longer forces `firstPage`. `splitPoints` (`lib/grading/batch.ts`, unit-tested) weighs candidates (named first page 3, first page without a name 1.5, name on an inside page 1, a repeat of the paper's name counts against) against the usual paper length (the gap between sure first pages that explains the stack best; a short paper costs 4.5 per typical length of shortfall, a long one 3), with fewer than 4 sure first pages it splits every candidate as before. Then `/api/grade-batch/split` reads the **first page of each paper again with `ClaudeService.readCoverName`** (GRADING_MODEL, Sonnet 5.5, with the class list, ~$0.01 a paper; returns `firstPage`, `written`, `student` + `sure`, title/course/period) and that name replaces Haiku's; a start that isn't a cover moves to the cover found within 2 pages. Haiku alone with a roster read 11 of 25 cover names right and kept returning the same few students; Sonnet got 25 of 25. The single grader's `/api/grading/read-header` uses `readCoverName` too (sends the roster). The review screen shows "usually N per paper" and an amber "9 pages, most have 9: check the split" chip (`typicalPageCount`, `pageCountLooksOff`), and the stack step has a tip to lay pages flat. Measured: 228 pages in ~75-150 s with 8 Haiku + 6 Sonnet workers (now 12 + 8). The route streams NDJSON (`{type:'status', step:'read'|'names', done, total}` then `{type:'done', headers}`; plan blocks are still plain 403 JSON first) and the page shows `SortingProgress`, a card with the four steps (getting pages ready, uploading, finding where papers start, reading names), a bar, counts, elapsed and a rough time left, in place of the form while sorting. **Eval**: `npx tsx --env-file=.env.local scripts/eval-page-split.ts <pages.json> --truth 0,9,18,... [--class id] [--cached headers.json]` (pages.json = `[{url}]` of Cloudinary pages in stack order; label the true first pages from contact sheets first). The client sends the roster as `{id, firstName, lastName}` objects (strings still accepted).
